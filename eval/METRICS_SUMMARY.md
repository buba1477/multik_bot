# Метрики RAG-поиска: обоснование архитектуры

## Введение

Цель исследования — выбрать оптимальные конфигурации поиска для двух популяций запросов:
**USER** (абстрактные, смысловые) и **EXACT** (точные реквизиты статей, номера НПА).

## Условия эксперимента

- **Дата замеров:** 28–30 октября 2026 г.
- **Модель эмбеддингов (Dense):** FRIDA (Sber RoBERTa) — `hf_cache/FRIDA`, **1536 dim**.
- **Модель реранкера (Cross-encoder):** `BAAI/bge-m3` (1024 dim) — `reranker/`.
- **Векторная база:** Qdrant (`fns_collection`, 5446 чанков, Cosine).
- **Датасеты:** USER — 76 запросов, EXACT — 145 запросов.
- **Железо:** GPU GTX 1660 Ti (для реранка, batch=4); retrieval — CPU (как в проде).

## Расшифровка метрик

Для оценки качества поиска мы используем 4 метрики. Вот что они означают на человеческом языке:

| Метрика | Что означает | Почему важна |
| :--- | :--- | :--- |
| **R@1 (Recall@1)** | Доля запросов, где **правильный ответ оказался на 1-м месте** | Самая строгая метрика: попал ли ответ сразу в «яблочко» |
| **R@3 (Recall@3)** | Доля запросов, где правильный ответ попал **в топ-3** | Показывает, насколько быстро пользователь найдёт ответ, если посмотрит первые 3 ссылки |
| **Hit@5** | Доля запросов, где **хотя бы один** правильный ответ попал **в топ-5** | **Главная метрика для UX**: в 88% случаев пользователь увидит правильный ответ на первой странице выдачи |
| **MRR@10** | Насколько **высоко** в среднем стоит первый правильный ответ (от 0 до 1) | Показывает качество ранжирования: если MRR = 1.0, правильный ответ всегда на 1-м месте |

**Пример:** Если Hit@5 = 88.1%, это значит: **в 88 из 100 запросов пользователь увидит хотя бы один правильный ответ в первых 5 результатах**. Для юридического чат-бота это критически важно — пользователь не должен уходить с пустыми руками.

## Этап 1. Выбор эмбеддингов (DENSE)

Сравниваем чистый DENSE (FRIDA) на обоих датасетах.

### USER (76 запросов)

| Конфигурация | R@1 | R@3 | Hit@5 | MRR@10 |
| :--- | :--- | :--- | :--- | :--- |
| dense | 0.468 | 0.670 | **0.881** | 0.808 |

### EXACT (145 запросов)

| Конфигурация | R@1 | R@3 | Hit@5 | MRR@10 |
| :--- | :--- | :--- | :--- | :--- |
| dense | 0.407 | 0.564 | **0.738** | 0.611 |

**Вывод:** DENSE (FRIDA) отлично работает на USER (Hit@5 = 88.1 %), но заметно проваливается на EXACT (73.8 %). Проблема: абстрактные эмбеддинги плохо различают точные номера статей.

## Этап 2. Добавление реранкера для EXACT

Пробуем полную ablation на EXACT-датасете.

| Конфигурация | R@1 | R@3 | Hit@5 | MRR@10 |
| :--- | :--- | :--- | :--- | :--- |
| DENSE | 0.407 | 0.564 | 0.738 | 0.611 |
| BM25 | 0.190 | 0.353 | 0.545 | 0.367 |
| HYBRID 0.50/0.50 | 0.400 | 0.580 | 0.759 | 0.619 |
| HYBRID 0.50/0.50 + Reranker (BAAI/bge-m3), pool=10 | 0.456 | 0.669 | **0.800** | 0.672 |

**Вывод:** на EXACT необходим HYBRID + реранкер BAAI/bge-m3.
Прирост Hit@5: 73.8 % → 80.0 % (**+6.2 п.п.** от DENSE; +4.1 п.п. к HYBRID без реранка, 75.9 %).
BM25 сам по себе слаб (54.5 %), но в гибриде даёт синергию.

> **Баланс качества/скорости (30.10.2026):** прод реранкует `combined_nodes[:10]` (engine_rag.py), т.е. работает pool=10.
> Ранее в eval-харнессе `--rerank-pool` игнорировался из-за бага замыкания дефолта аргумента (`pool: int = RERANK_POOL` замораживалось при импорте) — прогоны шли с pool=30 и давали Hit@5=86.2 % при ~20 с.
> После исправления (все 3 вызова `rerank_rank()` теперь передают `pool=` явно) честная прод-цифра: **Hit@5=80.0 % при lat_mean=6.85 с** (GPU, batch=4). Пул 30 даёт +6.2 п.п. (86.2 %), но латентность в ~3 раза выше.

## Этап 3. Проверка реранкера на USER

Как реранкер влияет на USER? Сравниваем DENSE с HYBRID + Reranker.

| Конфигурация | R@1 | R@3 | Hit@5 | MRR@10 |
| :--- | :--- | :--- | :--- | :--- |
| DENSE | 0.468 | 0.670 | **0.881** | 0.808 |
| HYBRID 0.65/0.35 + Reranker (BAAI/bge-m3) | 0.476 | 0.665 | 0.868 | 0.797 |

**Вывод:** реранкер на USER не улучшает качество (Hit@5 даже падает с 88.1 % до 86.8 %), но добавляет ~20 с латентности. Поэтому для USER оставляем чистый DENSE.

## Этап 4. Альтернативные реранкеры (лёгкие)

В поиске более лёгкой альтернативы BAAI/bge-m3 протестированы 4 модели (контейнер `eval_api`, GPU (CUDA), top_k=30). Полные отчёты — `eval_rerank_out/`.

### USER (76 запросов, hybrid_rerank 0.65/0.35)

| Реранкер | R@1 | Hit@5 | MRR@10 | lat_mean, ms |
| :--- | :--- | :--- | :--- | :--- |
| bge_base (лёгкая, 768 dim) | 0.223 | 0.750 | 0.524 | 6089.6 |
| minilm_l12 (bert, 384 dim) | 0.333 | **0.842** | **0.646** | 2031.9 |
| msmarco_minilm (bert, 384 dim) | 0.259 | 0.829 | 0.592 | 1297.8 |
| russian (bert, 768 dim) | **0.398** | 0.816 | 0.698 | 4781.7 |

### EXACT (145 запросов, hybrid_rerank 0.5/0.5)

| Реранкер | R@1 | Hit@5 | MRR@10 | lat_mean, ms |
| :--- | :--- | :--- | :--- | :--- |
| bge_base (лёгкая, 768 dim) | 0.259 | 0.738 | 0.501 | 5825.5 |
| minilm_l12 (bert, 384 dim) | **0.356** | 0.717 | 0.568 | 1760.7 |
| msmarco_minilm (bert, 384 dim) | 0.316 | 0.697 | 0.533 | 1019.0 |
| russian (bert, 768 dim) | 0.350 | **0.759** | **0.590** | 4768.2 |

> **Примечание:** bge_base (768 dim) ≠ прод-модель BAAI/bge-m3 (1024 dim). Легкие реранкеры тестировались в изолированном контейнере; прод-модель BAAI/bge-m3 участвовала только в основных прогонах Этапов 1–3.

**Вывод по этапу 4:** легкие реранкеры в 3–6 раз быстрее BAAI/bge-m3, но на EXACT заметно уступают ему по качеству (лучший среди лёгких — russian, 75.9 % Hit@5 против 80.0 % у bge-m3 (прод pool=10)). На USER они не актуальны, так как DENSE (88.1 %) остаётся недосягаем.

## Этап 5. Сравнение эмбеддингов (FRIDA vs E5-large)

В поиске альтернативы FRIDA протестирована модель multilingual-e5-large (1024 dim, окно 512 токенов). Эмбеддинги E5 индексированы в отдельную коллекцию fns_collection_e5, не затрагивая прод-коллекцию fns_collection. Сравнение проводилось на тех же датасетах (76 USER, 145 EXACT).

### USER (76 запросов, dense)

| Модель | R@1 | R@3 | Recall@10 | MRR@10 | lat_mean, мс |
| :--- | :--- | :--- | :--- | :--- | :--- |
| FRIDA | 0.458 | 0.583 | 0.833 | 0.556 | 260 |
| E5-large | 0.357 | 0.549 | 0.765 | 0.688 | 151 |

### EXACT (145 запросов)

| Модель | config | R@1 | R@3 | Recall@10 | MRR@10 | lat_mean, мс |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| FRIDA | dense | 0.444 | 0.717 | 0.859 | 0.591 | 298 |
| E5-large | dense | 0.397 | 0.605 | 0.744 | 0.598 | 137 |
| FRIDA | hybrid@0.5/0.5 | 0.475 | 0.737 | 0.909 | 0.621 | 312 |
| E5-large | hybrid@0.5/0.5 | 0.358 | 0.559 | 0.752 | 0.579 | 162 |

> **Примечание:** hybrid_rerank для E5 не запускался, так как реранкер BAAI/bge-m3 — общий cross-encoder; его результаты на FRIDA переносимы на E5-пайплайн.

**Вывод по этапу 5:** FRIDA выигрывает по Recall (полноте поиска) на обоих датасетах:

На USER: R@1 = 45.8 % (E5 — 35.7 %), Recall@10 = 83.3 % (E5 — 76.5 %).

На EXACT: R@1 = 44.4 % (E5 — 39.7 %), Recall@10 = 85.9 % (E5 — 74.4 %).

E5 быстрее в 1.7–2.0 раза (151 мс против 260 мс на USER; 137 мс против 298 мс на EXACT) и выигрывает по MRR на USER (0.688 против 0.556), то есть лучше ранжирует если находит правильный ответ. Но для юридических консультаций ФНС критична полнота — чтобы правильная статья вообще попала в выдачу. FRIDA делает это значительно лучше.

Поэтому FRIDA остается основной моделью эмбеддингов.

## Итоговый вывод

| Сценарий | Режим поиска | Эмбеддер / Реренкер | Веса RRF | Hit@5 | Время (mean) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **USER** (абстрактные, смысловые) | **DENSE** | FRIDA (1536 dim) | — | **88.1 %** | ~50 мс |
| **EXACT** (точные реквизиты) | **HYBRID + Reranker** | FRIDA + BM25 + BAAI/bge-m3 (1024 dim) | 0.50/0.50 | **80.0 %** | ~6.9 с (GPU, pool=10) |

Адаптивный классификатор (`classifier.py`) автоматически определяет тип запроса и переключает режимы. Это даёт 50 мс для USER и ~7 с (GPU, pool=10) для EXACT там, где нужна максимальная точность.
