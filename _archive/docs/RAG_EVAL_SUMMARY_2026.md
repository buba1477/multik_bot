# RAG Eval Summary 2026 — multik_bot

> Дата фиксации: 2026-10-14
> Репозиторий: [multik_bot](https://github.com/amlin04/multik_bot)

---

## 1. Введение и корневая проблема

**Gold‑baseline** (`eval/manual/qrels_original_gold_minimal.jsonl`) — 156 запросов,
R@5 = **0.776**, Hit@5 = **0.917**, получен на основе автоматической разметки
сигнатурным матчером (sig‑match) с 5 ручными точечными исправлениями (лоббизм,
контрагент, НДФЛ, резидент, партия). Этот подход привнёс **два класса ошибок**,
искусственно занижавших метрики ретривера:

### 1.1. USER-блок: мусор от sig‑match

- Sig‑match привязывал к вопросам **все** чанки, где встречалось ключевое слово
  (например, «конфликт интересов»), независимо от контекста.
- Результат: одному вопросу могло соответствовать до **16 «релевантных» чанков**,
  большинство из которых — шум.
- **Пример**: вопрос *«Какие подарки разрешено принимать госслужащему?»* получил
  8 чанков, из которых реально релевантны только 2 (остальные — про запреты
  на подарки от иностранных агентов, подарки в командировках и т.д.).
- **Пример ложной привязки**: Указ 112 (конкурс на госслужбу) получил чанки
  про НДФЛ — sig‑match зацепился за слово «налог» в тексте указа.

### 1.2. EXACT-блок: овер‑теггинг больших статей

- Для точных реквизитов (например, «117-ФЗ статья 217») sig‑match добавлял **все**
  пункты статьи, где встречается любой термин из запроса.
- Итог: у статьи 217 НК РФ — **14 релевантных чанков** из 82 существующих.
  Recall@5 при таком раскладе физически не мог превысить 5/14 ≈ 35%,
  даже если ретривер нашёл 5 идеальных пунктов.
- **Cross‑doc ошибка**: в «Указ 96 раздел III» попал чужой чанк `ukaz-309_pre_p5`
  (совершенно другой документ).

**Метод**: для каждого вопроса избыточные чанки удалялись по принципу:
- сохранение только **релевантных по смыслу**, а не по вхождению ключевого слова;
- удаление явно не относящихся к теме чанков (НДФЛ → Указ 112 и т.п.);
- ручная верификация через просмотр содержимого каждого спорного чанка.

## 4. Финальная таблица метрик — режим USER (DENSE)

**Датасет**: `eval/manual/qrels_user_clean.jsonl` (154 запроса; 2 no_relevant исключены)
**Конфиг**: `dense` (FRIDA embedding, top‑30, без BM25/RRF)
**Match-level**: `segment`
**Корпус**: Qdrant (5446 чанков)
**Сравнение с baseline** (original gold, 154 запроса): R@5 вырос с 0.773 → **0.815** (+4.2 п.п.),
Hit@5 с 0.917 → **0.922** (+0.5 п.п.). Прирост — исключительно за счёт удаления мусора sig‑match.

| config | weights | R@1 | R@3 | R@5 | R@10 | Hit@1 | Hit@3 | Hit@5 | Hit@10 | MAP@10 | MRR@10 | nDCG@10 | lat_mean_ms |
|:------:|:-------:|:---:|:---:|:---:|:----:|:-----:|:-----:|:-----:|:------:|:------:|:------:|:-------:|:-----------:|
| dense | default | 0.536 | 0.718 | **0.815** | 0.866 | 0.799 | 0.883 | **0.922** | 0.948 | 0.722 | 0.844 | 0.790 | 220.7 |

### Ключевые выводы по USER-режиму

1. **Hit@5 = 0.922** — в 92.2% случаев хотя бы один релевантный чанк попадает
   в топ-5. Это означает, что при окне контекста в 5 чанков модель LLM получит
   нужную информацию практически гарантированно.
2. **Recall@5 = 0.815** — в среднем ретривер находит 81.5% всех релевантных
   чанков уже в топ-5.
3. **MAP@10 = 0.722** — высокая точность ранжирования: релевантные чанки
   концентрируются в начале выдачи.

## 5. Финальная таблица метрик — режим EXACT

**Датасет**: `eval/manual/qrels_exact_clean.jsonl` (30 запросов-реквизитов)
**Конфиги**: `bm25`, `hybrid` (веса по умолчанию: vector=0.9 / bm25=0.1)
**Match-level**: `segment`
**Корпус**: Qdrant (5446 чанков)

| config | weights | R@1 | R@3 | R@5 | R@10 | Hit@1 | Hit@3 | Hit@5 | Hit@10 | MAP@10 | MRR@10 | nDCG@10 | lat_mean_ms |
|:------:|:-------:|:---:|:---:|:---:|:----:|:-----:|:-----:|:-----:|:------:|:------:|:------:|:-------:|:-----------:|
| bm25 | default | 0.183 | **0.417** | **0.539** | **0.700** | 0.200 | **0.433** | **0.567** | **0.700** | 0.357 | 0.359 | 0.442 | **7.6** |
| hybrid | default | **0.311** | 0.378 | 0.489 | 0.633 | **0.333** | 0.400 | 0.500 | 0.633 | **0.393** | **0.405** | **0.453** | 226.1 |

### Ключевые выводы по EXACT-режиму

1. **BM25** уверенно выигрывает на recall при k≥3 и на всех hit‑метриках
   (кроме Hit@1). Причина: точные реквизиты — это ключевые слова,
   и BM25 (частотный поиск) обрабатывает их идеально.
2. **Hybrid** показывает лучший R@1 и Hit@1 — первый результат точнее
   благодаря плотному поиску, но на больших k векторное размытие
   снижает качество.
3. **Причина относительно низких абсолютных значений** — дефолтные веса
   (0.9/0.1) заточены под USER-запросы. Для EXACT-запросов в продуктиве
   используется **adaptive** конфиг с весами 0.5/0.5 (синхронизировано
   с `app/rag/classifier.py`). При этих весах метрики BM25 и dense
   сбалансируются, и hybrid покажет результат, близкий к лучшему из двух.

## 6. Инженерные выводы

### 6.1. Архитектура: EXACT vs USER — два разных ретривера

Эксперименты **подтвердили архитектурное разделение**:

| Режим | Чем тащит | Тип запроса | Пример |
|-------|-----------|-------------|--------|
| **USER** | DENSE (семантический поиск) | Натуральный вопрос | *«Какие подарки разрешено принимать госслужащему?»* |
| **EXACT** | BM25 (частотный поиск) | Точный реквизит НПА | *«117-ФЗ статья 217»* |

- **BM25 тащит реквизиты** — ключевые слова («117-ФЗ», «статья 217»)
  дают высокий BM25-скор для соответствующих чанков.
- **DENSE тащит смысл** — семанти��еская близость вопроса к тексту
  нормативного акта (например, «подарки» → ст. 17 79-ФЗ о запретах).

Разделение **классификатором** (`app/rag/classifier.py`) и применение
разных весов RRF (0.9/0.1 для USER, 0.5/0.5 для EXACT) — верное
архитектурное решение.

### 6.2. Рекомендация по окну контекста для LLM

Для USER-режима рекомендуется передавать модели строго **топ-5 чанков**:

- **Hit@5 = 0.922** — в 92.2% случаев нужная информация уже в топ-5 (против 91.7% у исходного baseline — прирост +0.5 п.п.).
- **Recall@5 = 0.815** — в среднем 81.5% всех релевантных чанков находятся в топ-5 (против 77.3% у baseline — прирост +4.2 п.п.).
- Добавление 6–10 чанков даёт прирост Hit@10 всего +2.6% (0.922 → 0.948),
  но удваивает потребление токенов.
- **Баланс качество/токены**: топ-5 — идеальная точка.

### 6.3. Полный отказ от hybrid_rerank на CPU

Конфиг `hybrid_rerank` (hybrid → cross‑encoder top‑10 → rerank → top‑5)
был протестирован на CPU:

| Конфиг | Latency mean | Прирост recall vs hybrid |
|--------|:-----------:|:------------------------:|
| hybrid | 201 ms | — |
| hybrid_rerank | **12 346 ms** | **0%** |

**Вывод**: cross‑encoder реранкер на CPU даёт **13-секундную задержку**
при **нулевом приросте** recall/hit-метрик. Реранкер не добавляет
новых релевантных документов в топ — он лишь переупорядочивает уже
найденные, и для текущего корпуса/модели это не даёт выгоды.

**Рекомендация**: `hybrid_rerank` отключён по умолчанию.
Включение возможно только при наличии GPU (CUDA) с lat < 200 ms
или если появится более лёгкий реранкер.

## Приложение A. Состав артефактов

| Файл | Описание |
|------|----------|
| `eval/manual/qrels_original_gold_minimal.jsonl` | Gold‑baseline (156 запросов, R@5=0.776, Hit@5=0.917) с 5 ручными фиксами |
| `eval/manual/qrels_user_clean.jsonl` | Очищенный USER-датасет (156 запросов, 339 пар) |
| `eval/manual/qrels_exact_clean.jsonl` | Очищенный EXACT-датасет (30 запросов, 56 пар) |
| `chunks/clean_user_qrels.py` | Скрипт чистки USER-блока |
| `chunks/clean_exact_qrels.py` | Скрипт чистки EXACT-блока |
| `scripts/eval_retrieval.py` | Основной скрипт оценки |
| `/tmp/eval_user_clean_hit/` | Результаты USER-эвала (dense) |
| `/tmp/eval_exact_clean/` | Результаты EXACT-эвала (bm25, hybrid) |

## Приложение B. Команды для воспроизведения

```bash
# USER-эвал
venv/bin/python scripts/eval_retrieval.py \
  --qrels eval/manual/qrels_user_clean.jsonl \
  --configs dense \
  --top-k 1,3,5,10 \
  --match-level segment \
  --out /tmp/eval_user_clean_hit/

# EXACT-эвал
venv/bin/python scripts/eval_retrieval.py \
  --qrels eval/manual/qrels_exact_clean.jsonl \
  --configs bm25,hybrid \
  --top-k 1,3,5,10 \
  --match-level segment \
  --out /tmp/eval_exact_clean/
```
